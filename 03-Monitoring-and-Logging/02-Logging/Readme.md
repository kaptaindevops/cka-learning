# Logging in Kubernetes

Before understanding logging in Kubernetes, it helps to first look at how logging works in Docker.

## Logging in Docker

Consider a Docker container that runs an application called **Event Simulator**. This application continuously generates random events that simulate web server activity and writes these events to the **standard output (stdout)**.

If the container is started in **detached mode**, the logs are not displayed directly in the terminal:

```bash
docker run -d event-simulator

```

Since the container runs in the background, you will not see the log output. To view the logs of the container, you can use the following command:

```bash
docker logs <container-id>

```

If you want to watch the logs in real time, you can use the `-f` (follow) option:

```bash
docker logs -f <container-id>

```

This allows you to stream logs live as the application generates them.

---

## Logging in Kubernetes

In Kubernetes, applications run inside Pods, which may contain one or more containers. If a Pod runs a container that writes logs to standard output, Kubernetes can capture those logs.

To view logs from a container running inside a Pod, use the following command:

```bash
kubectl logs <pod-name>

```

This command displays the logs generated by the container in that Pod.

If you want to stream logs continuously, use the `-f` option:

```bash
kubectl logs -f <pod-name>

```

This behaves similarly to the Docker log streaming command.

---

## Logging in Multi-Container Pods

A Pod in Kubernetes can contain multiple containers. In such cases, the `kubectl logs` command needs to know which container's logs you want to view.

**Example Pod structure:**

```text
Pod
 ├── event-simulator
 └── image-processor

```

If you run the logs command without specifying a container name, Kubernetes will return an error asking you to choose a container. To view logs for a specific container, use the `-c` option:

```bash
kubectl logs <pod-name> -c event-simulator

```

This command shows logs exclusively for the `event-simulator` container.

You can also stream logs from that specific container using:

```bash
kubectl logs -f <pod-name> -c event-simulator

```

## Basic vs. Advanced Logging

### Basic Logging in Kubernetes

The logging mechanism described above is the basic logging functionality built into Kubernetes. For most application developers, this is sufficient to:

* View application logs
* Troubleshoot issues
* Monitor application output

> **Note:** These commands are commonly used during troubleshooting and are highly important for Kubernetes certification exams.

### Advanced Logging

While basic logging works well for development and debugging, production environments usually require more advanced logging capabilities. Examples include:

* Centralized log storage
* Log aggregation from multiple nodes
* Searchable logs
* Long-term log retention

To achieve this, Kubernetes environments often integrate with external logging systems. These tools collect logs from containers across the cluster and store them in centralized logging platforms. Popular solutions include:

* **ELK Stack** (Elasticsearch, Logstash, Kibana)
* **Fluentd**
* **Loki**
* **Splunk**

---

## Summary

Logging in Kubernetes works similarly to Docker because containers typically write logs to standard output.

**Key commands include:**

| Task | Command |
| --- | --- |
| **View Pod logs** | `kubectl logs <pod-name>` |
| **Stream logs in real time** | `kubectl logs -f <pod-name>` |
| **View logs for a specific container** | `kubectl logs <pod-name> -c <container-name>` |

These commands provide a simple way to access application logs and troubleshoot issues in Kubernetes workloads.
